# 画像OCR・説明文生成アプリ

画像や PDF をアップロードすると、マルチモーダル LLM（Claude）を使って
ファイル内の文字起こし（OCR）と内容の説明を生成する Web アプリケーションです。

## 主な機能

- 画像（JPEG / PNG）・PDF のアップロードとプレビュー表示
- LLM による以下の生成・表示
  - **OCR**: ファイル内の文字を抽出したテキスト
  - **内容の説明**: ファイルに何が写っている / 書かれているかの説明
  - **タグ**: 内容を表すキーワード（複数）
  - **代替テキスト（alt）**: アクセシビリティ用の簡潔な説明
- API 処理中のローディング表示
- エラー時のメッセージ表示（日本語）

すべての出力・UI は日本語です。

## セットアップ・起動手順

### 前提

- Docker および Docker Compose がインストールされていること
- Anthropic API キー（https://console.anthropic.com で取得）

### 手順

1. リポジトリのルートに `.env` ファイルを作成します（`.env.example` をコピー）:

```bash
   cp .env.example .env
```

2. `.env` に Anthropic API キーを設定します:
```bash
   ANTHROPIC_API_KEY=sk-ant-xxxxx
```
3. Docker Compose で起動します:

```bash
   docker compose up --build
```

4. ブラウザで以下にアクセスします:

   - フロントエンド: http://localhost:5273
   - バックエンド API ドキュメント（Swagger）: http://localhost:8005/docs

`.env` の `FRONTEND_PORT` / `PORT` でホスト側ポートを変更できます。

## 使用した LLM API・技術スタック

### LLM API

- **Anthropic Claude**（マルチモーダル対応モデル）
  - Vision API で画像を解析
  - Tool Use（Function Calling）で構造化された出力を強制

### バックエンド

- **Python 3.12 / FastAPI** — REST API
- **PyMuPDF** — PDF を画像に変換
- **Pydantic** — スキーマ定義とバリデーション
- **pytest** — テスト（11 ケース）

### フロントエンド

- **React 18 / Vite** — UI
- 自ホストのバリアブルフォント（Inter / Space Grotesk / JetBrains Mono）

### インフラ

- **Docker / Docker Compose** — フロントエンド・バックエンドを 1 コマンドで起動

## 設計上の判断や工夫した点

### Tool Use による構造化出力の強制

OCR・説明・タグ・alt の 4 項目を確実に取得するため、プロンプトで
JSON を依頼するのではなく、Claude の Tool Use 機能を使用しました。
`tool_choice` でツールの使用を強制することで、散文ではなく必ず
スキーマに沿った構造化データが返るようにしています。さらに受信後に
Pydantic で再検証し、外部 API のレスポンスを盲信しない二重の防御と
しています。

### PDF を画像に統一

Claude は PDF を直接扱えますが、将来的に他のプロバイダー（OpenAI 等）を
追加した場合の入力形式の一貫性を考慮し、バックエンドで PDF を PNG に
変換してから LLM に渡す方針としました。PyMuPDF は純粋な Python wheel で
システム依存（poppler 等）が不要なため、Docker イメージに含めやすい点も
採用理由です。

### エラーハンドリングの分離

外部 API の生のエラー（スタックトレースや内部詳細）はサーバーログに
記録し、ユーザーには理解しやすい日本語メッセージのみを返すよう分離
しました。内部情報の漏洩を防ぎ、UX を向上させています。エラーレスポンスは
`{ "error": { "code": "...", "message": "..." } }` の一貫した構造とし、
フロントエンドは `code` で分岐でき、`message` をそのまま表示できます。

### フロントエンドとバックエンドの通信

Vite の proxy 機能で `/api` へのリクエストをバックエンドに転送し、
フロントエンドは同一オリジンのパスのみを使用します。これにより CORS の
問題を回避し、フロントエンドのコードにバックエンドの URL を
ハードコードせずに済みます。

### 接続状態のポーリング

バックエンドの接続状態表示は、状態に応じてポーリング間隔を動的に変更
します。未接続時は短間隔（5秒）で素早くリトライし、接続確立後は長間隔
（3分）に切り替えて不要なリクエストを抑えます。`depends_on` はコンテナの
起動順しか保証しないため、起動タイミングのずれに状態の最終的な整合性で
対応しています。

### 設定と定数の分離

環境によって変わりうる値（ポート、API キー、ファイルサイズ上限）は
環境変数 / 設定として管理し、ドメインのルール（対応ファイル形式など）は
コード内の定数として保持しました。API キーは環境変数で管理し、ソース
コードにハードコードしていません。

### クロスアーキテクチャ対応の Docker

Docker イメージはビルド環境のアーキテクチャ（Apple Silicon の arm64、
x86 の amd64 など）に自動的に対応するよう構成しています。

## エラーハンドリング

- **不正なファイル形式**: 対応形式（JPEG / PNG / PDF）以外は 400 エラー
- **空ファイル / サイズ超過**: バリデーションエラー
- **LLM API の失敗**: 502 エラー（ユーザーには汎用メッセージ、詳細はログ）
- **サーバー未接続**: フロントエンドでネットワークエラーを表示

フロントエンドの入力制限（`accept` 属性）に加え、バックエンドでも
バリデーションを行う二重チェックとしています。

## テスト

バックエンドのテストは Docker コンテナ内で実行します:

```bash
docker compose exec backend pytest -v
```

Claude API はモック化しているため、テスト実行時に実際の API 呼び出しは
発生しません。フロントエンドは手動テストで動作を確認しています。
